# Platform and measurement constraints

## Android 16 and background monitoring

The runtime target is Android 16/API 36. Compile SDK 37 is required by existing AndroidX dependencies; compiling against it does not change the runtime target or minimum supported API 26. The baseline alpha Compose BOM required 37.1 despite declaring 37.0; the stable BOM avoids that mismatch.

Continuous, user-visible battery monitoring uses `specialUse`, with its use case declared in the manifest. Battery monitoring is not human health tracking. `dataSync` has a six-hour background limit on Android 15+ and is unsuitable for indefinite monitoring. Google Play submission still requires review of the declared special-use purpose; local installation does not prove Play approval.

Android 16 enforces edge-to-edge layouts and enables predictive back. Screens must respect system insets and remain usable after rotation, at large font sizes and on larger windows.

The manifest declares `QUERY_ALL_PACKAGES` so per-app battery use can name and draw the icon of any app batterystats reports, including ones with no launcher entry. This is a Play-review-gated permission: Play can reject a submission over its declared use even though the local build installs fine. GitHub and F-Droid distribution are not subject to that review and are unaffected.

Sources: [foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types), [timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout), [Android 16 changes](https://developer.android.com/about/versions/16/behavior-changes-16).

## Shizuku and other access modes

Shizuku user services run as shell or root, depending on how Shizuku was started. Shell access does not grant every root-only capability. A running service and authorization are separate states. Reads must carry their actual source and failure state; incomplete output is not a successful sample. Reconnection starts a new baseline for cumulative differences. Root and ADB-granted modes remain supported, with their respective permission limits.

Non-root Shizuku (started from the Shizuku app over ADB, without a root-based starter) does not survive a reboot on its own: the user has to start it again after every restart. In practice this means a meaningful share of sessions on non-rooted devices will show the per-app screen's NO_ACCESS state until Shizuku is restarted; this is expected Shizuku behavior, not a Voltwise bug. ADB grants may persist across reboot, but on Android 16/API 36 cross-user refusal prevents ADB-only access to per-app batterystats; that capability requires Shizuku or root. Backend selection uses Shizuku when running and authorized, otherwise root, then ADB where the platform permits it.

For ADB-granted reads, Android 16 `BatteryStatsService` checks DUMP plus PACKAGE_USAGE_STATS permission and an allowed/default usage app-op. BATTERY_STATS alone does not authorize dumps. On API 36, cross-user refusal still prevents ADB-only per-app batterystats access; Shizuku or root is needed for that capability. `--proto --charged` requests the current aggregate reporting window. The fixed command captures bounded binary stdout before encoding it for the helper pipe; stderr is drained separately, and refusal, truncation, timeout and oversized responses are failures. Names remain length-delimited metadata. `--checkin` can instead consume a saved completed report and is not the app-statistics source.

Sources: [Android16 BatteryStatsService](https://github.com/aosp-mirror/platform_frameworks_base/blob/android16-release/services/core/java/com/android/server/am/BatteryStatsService.java), [DumpUtils](https://github.com/aosp-mirror/platform_frameworks_base/blob/android16-release/core/java/com/android/internal/util/DumpUtils.java).

Source: [Shizuku API and UserService lifecycle](https://github.com/RikkaApps/Shizuku-API/blob/master/README.md).

## Sensor contracts and screen state

Android reports current in microamperes (positive into the battery), charge in microampere-hours and remaining energy in nanowatt-hours. Unsupported long properties return `Long.MIN_VALUE`. Average-current hardware windows vary. `computeChargeTimeRemaining()` (API 28+; gated behind `Build.VERSION_CODES.P`) is a system approximation, not a guaranteed completion time. `EXTRA_CYCLE_COUNT` is only read on API 34+ (`Build.VERSION_CODES.U`); on earlier versions cycle count is unavailable. Vendor unit/sign violations are corrected automatically, but only from evidence — comparing raw current against the charge counter's own change over matching windows — never by assuming every small value uses different units; a correction that changes the effective value is shown with an Undo, and the counter itself is sanity-checked but never rescaled. See [measurement guide](MEASUREMENTS.md#automatic-calibration) for the detection rule.

`PowerManager.isInteractive()` reports readiness for interaction, not whether every display pixel is lit. Noninteractive ambient/Always On Display belongs to the screen-off category in this app's observation model. Screen-off, CPU suspend and Android Doze are distinct. Executing app code cannot establish that the CPU is asleep at that instant; elapsed/uptime differences describe past intervals.

Sources: [BatteryManager](https://developer.android.com/reference/android/os/BatteryManager), [PowerManager](https://developer.android.com/reference/android/os/PowerManager#isInteractive()), [Android 16 checkin producer](https://github.com/aosp-mirror/platform_frameworks_base/blob/android16-release/core/java/android/os/BatteryStats.java).

## Quick Settings tile and dynamic color gates

The Quick Settings tile's `Tile.subtitle` only exists from API 29 (`Build.VERSION_CODES.Q`); below that the current/power text is shown as the tile's `label` instead. Long-press opening the app from the tile uses `startActivityAndCollapse(PendingIntent)` from API 34 (`Build.VERSION_CODES.UPSIDE_DOWN_CAKE`); below that it falls back to the deprecated `startActivityAndCollapse(Intent)` overload, which only exists pre-34. Dynamic (Material You) color is opt-in and only applied from API 31 (`Build.VERSION_CODES.S`); below that, or with the setting off, the app uses its fixed dark palette.

## Samsung verification boundary

Samsung documents that deep-sleeping apps only run when opened. If monitoring stops, inspect Settings → Battery → Background usage limits for Voltwise and Shizuku; menu wording varies by One UI version. Never-sleeping settings may help but are not proof that a service cannot be stopped. Do not disable device-wide protections as a generic workaround.

No physical Samsung device is available. Emulated sensor inputs cannot validate Samsung current polarity/scaling, capacity calibration, actual AOD events, OEM process management, or physical battery overhead. Functional tests and screenshots must identify their emulator/API and distinguish injected inputs from real readings.

Source: [Samsung background usage limits](https://www.samsung.com/us/support/answer/ANS10003442/).

## Advanced statistics contracts

Advanced app statistics use `dumpsys batterystats --proto --charged` on Android 9/API 28 and later. Android 8.0/8.1 have no aggregate proto output, so advanced app statistics are unavailable there; ordinary battery monitoring and history continue. Unsupported OEM output remains unavailable. A bounded wire decoder keeps app-chosen names inside their own UID records. The legacy checkin decoder is retained for compatibility fixtures; unescaped checkin names cannot certify app measurements.

The aggregate proto supplies UID total, screen and proportional charge estimates. The proportional value is an alternative total, not an extra amount to add. Per-UID component energy beyond screen/smear remains unknown. Activity counters cannot establish energy or causation. Job/sync totals use pooled timer duration; their background time uses actual total duration. Mobile-active UID time is already milliseconds in proto. Global Bluetooth energy is reported as an integer mAh estimate. Unknown global power-component enum values are omitted rather than assigned invented labels. Idling counters are not Doze maintenance windows. Raw UID/user identity is retained, and shared/removed/profile limitations remain visible.

Sources: [Android 16 aggregate schema](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-16.0.0_r2/core/proto/android/os/batterystats.proto), [Android 16 producer](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-16.0.0_r2/core/java/android/os/BatteryStats.java), [Android 8.1 supported dump options](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-8.1.0_r1/services/core/java/com/android/server/am/BatteryStatsService.java).

Android16 also documents `dumpsys batterystats --usage` and `--usage --proto`; these are possible component-report sources, but have different schemas/windows and cannot be silently merged into the aggregate snapshot. Existing UI component fields were never populated. They now show only fields this source actually reports; device component estimates and per-UID activity remain available. A separate validated component transport would be required before presenting additional per-UID estimates.

Kernel attributes use µV, µA, µAh, µWh, seconds and tenths Celsius by ABI. Full-charge capacity is a remembered gauge threshold, not a laboratory capacity measurement. CPU `time_in_state` uses10ms usertime units and covers time since driver load/reset, which can differ from time since boot.

Sources: [Linux power supply class](https://cdn.kernel.org/doc/html/latest/power/power_supply_class.html), [CPU frequency statistics](https://kernel.org/doc/html/latest/cpu-freq/cpufreq-stats.html).

## Privileged actions in Insights

Insights can change a few Android settings for an app, but only after the user taps the fix in an apply dialog; nothing is applied automatically, and a notification only opens the Insights tab. How a finding is computed is in the [measurement guide](MEASUREMENTS.md#insights).

**Access.** Actions run only through `ShellRunner.execAction`, which accepts Shizuku or root. With ADB-only or no access it returns `NoAccess` ("Actions require Shizuku or root") and the app shows the fix as needing access, with the settings shortcuts still available. Each command chooses one backend and does not silently try another backend on failure. A subsequent readback can use a newly available backend; a mutation is never replayed automatically after a lost response. Standby-bucket, background app-op and force-stop commands target user 0 (`--user 0`). App-targeted privileged fixes validate an installed user-0 package using the calling user's own package view; UID guards reject other-profile targets. Doze whitelist removal and Undo instead change Android's device-wide user-added package/appId whitelist, so they can affect copies of the same package in other profiles or users. Here, “user whitelist” means user-added. See AOSP Android 16 r2's [DeviceIdleController](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-16.0.0_r2/apex/jobscheduler/service/java/com/android/server/DeviceIdleController.java) and [PowerManagerService](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-16.0.0_r2/services/core/java/com/android/server/power/PowerManagerService.java).

**Exact commands.** Each is a fixed template in `PrivilegedCommand`; callers cannot supply command text. Package names must match `[A-Za-z][A-Za-z0-9_]*(\.[A-Za-z][A-Za-z0-9_]*)+` and be at most 255 characters, and the joined command may contain only letters, digits and `_.+-` between single spaces, so no shell syntax reaches `su -c`. `ShellRunner` and the Shizuku helper (`ShellUserService`) both check the argv against the same `CommandPolicy.allows` list, which rejects everything else.

| Purpose | Command | Gating |
| --- | --- | --- |
| Read standby bucket | `am get-standby-bucket --user 0 <pkg>` | API 28+ |
| Set standby bucket (Restrict: `restricted`; rare fallback: `rare`; Undo: the recorded bucket) | `am set-standby-bucket --user 0 <pkg> <active\|working_set\|frequent\|rare\|restricted>` | API 28+; `restricted` needs API 30+, so Restrict on API 28–29 sets `rare` and says so |
| Read background app-op | `cmd appops get --user 0 <pkg> RUN_ANY_IN_BACKGROUND` | `RUN_ANY_IN_BACKGROUND` on API 28+; existing API 26–27 journal rows retain `RUN_IN_BACKGROUND` for Undo/reconciliation |
| Restrict background (Undo: the recorded mode) | `cmd appops set --user 0 <pkg> RUN_ANY_IN_BACKGROUND ignore` (Undo writes `allow` or `ignore`) | new fixes are offered on API 28+ only; Undo restores the journal's recorded op, including legacy `RUN_IN_BACKGROUND` |
| List Doze whitelist | `cmd deviceidle whitelist` | read-only; also run during each analysis when access exists |
| Remove from Doze whitelist / Undo | `cmd deviceidle whitelist -<pkg>` / `cmd deviceidle whitelist +<pkg>` | device-wide user-added whitelist entries only |
| Force-stop | `am force-stop --user 0 <pkg>` | one-shot |

`dumpsys deviceidle` is also on the read-only list. `EXEMPTED` and `NEVER` buckets and the `deny`, `default` and `foreground` app-op modes can be read but are never written. Fixes that need no access are plain Android intents: **OPEN_APP_SETTINGS** opens `android.settings.APPLICATION_DETAILS_SETTINGS` for the package and **OPEN_BATTERY_OPTIMIZATION_SETTINGS** opens `android.settings.IGNORE_BATTERY_OPTIMIZATION_SETTINGS`; the high-battery-alert fix only turns on Voltwise's own alert setting. Below API 28 the bucket and new background-restriction fixes are refused as unsupported: on API 26–27 `RUN_IN_BACKGROUND` has no effect on apps targeting API 26+, so “Restrict background” is offered on API 28+ only. Existing legacy app-op journal rows can still be undone and reconciled. Apps known to be on the user Doze whitelist are offered whitelist removal first instead of “Restrict background” and the restricted-bucket fix, because Android exempts those apps from the restrictions; settings and force-stop shortcuts remain where applicable. Unknown whitelist membership preserves the usual recommendations.

**Protected targets.** A fix is refused when the package is Voltwise itself (release, debug and preview ids), `moe.shizuku.privileged.api`, `android`, `com.android.systemui`, `com.android.phone` or `com.google.android.gms`, when its UID is below 10000, or when its UID belongs to another user (UID ÷ 100000 ≠ 0). It is also refused when the package is not installed for user 0, when its installed UID differs from the one in the finding, when it shares its UID with other packages, or when it is the current default home, dialer, SMS or input-method app (best-effort lookups with public APIs; other roles are not detected). The shared-UID and role checks apply to applying only, so a restore still works afterwards. Refusals are reported as fixed codes (not privileged, protected, not installed, UID mismatch, shared UID, role holder, unsupported SDK, invalid package, unrestorable prior state, inspection failed, already at target) and never name the package in diagnostics.

**Transport loss.** Read-only Shizuku commands may reconnect and retry once. Privileged mutations are dispatched at most once per confirmed attempt; a lost response can mean the command took effect, so it is not automatically replayed. Reversible actions still use a fresh state read to establish the outcome.

**Readback and OEM variance.** After every reversible write the same state is read again and compared. Accepted forms are the standby bucket as its name or number; a single `RUN_ANY_IN_BACKGROUND: <mode>` app-op record (optionally with `mode:` and trailing `time=`/`duration=` fields); `No operations.`, which reads as the effective `allow` unless one `Default mode:` line gives another mode; and whitelist lines of the form `user|system|system-excidle,<pkg>,<appId>`. Anything else (another op's record, several or conflicting records, an empty whitelist, unexpected text) is *unrecognised* and is never read as the requested state or as the old state: an initial read fails with READ_FAILED and leaves no journal row; after PREPARED, the action ends UNKNOWN rather than being reported as applied or failed. Output formats differ between Android versions and OEM builds, so this is the expected outcome on a build whose output the parser does not know. A mutation's own acknowledgement (`Added:`/`Removed:`) is not used as confirmation; the list is read again. A prior app-op state that is not `allow` or `ignore`, or a prior bucket that is `exempted` or `never`, makes the fix refuse (unrestorable prior state), so Undo can always restore exactly what was there. A bucket set from the shell is treated by Android as user-forced until the app is next used; Undo restores the recorded bucket but cannot stop the system re-bucketing the app afterwards.

**Action journal.** Each fix is a row in `insight_actions` (package, UID, user, type, prior and target state, timestamps, and a fixed status code). The whole action runs under one lock: revalidate the target, read its current state, write a PREPARED row with the prior and target state, execute, read back, then record APPLIED (state equals target), FAILED (state unchanged from the prior) or UNKNOWN (readback loses access or is unreadable or unrecognised, a third state, or the prior state after a command whose failure is unconfirmed); a command refused for lack of access ends FAILED. A failed or unreadable first read, or no access at that point, returns a refusal or failure and leaves no row. Force-stop has no prior state: an UNKNOWN attempt is inserted before dispatch, so a journal-insert failure prevents the command. A confirmed successful command settles that same row as ONE_SHOT, a known failure as FAILED, and an unconfirmed dispatch, cancellation or failed settlement leaves the durable UNKNOWN attempt. UNKNOWN force-stop rows claim no applied fix and authorize no Undo; a later explicitly confirmed attempt remains available.

**Reconciliation.** If the process dies between PREPARED and confirmation, the app start re-reads each recoverable PREPARED or UNKNOWN row and never replays its command (force-stop has no restorable state): state equal to the target becomes APPLIED; equal to the prior becomes REVERTED when an application was previously established (including an interrupted Undo), otherwise FAILED; anything else (or unreadable, for instance without access) stays UNKNOWN to be retried later. A package that has been uninstalled or reinstalled under a different UID is marked REVERTED without a command.

**Undo.** Available for reversible APPLIED and UNKNOWN rows. It revalidates the target (protected, invalid-package and inspection failures still refuse; shared-UID and role-holder checks do not), reads the current state, and if it is not the recorded target reports that the setting was changed outside Voltwise and writes nothing. Otherwise it marks the row UNKNOWN, writes the prior state, reads it back and records REVERTED when it matches. If the read shows the target still in place, the row returns to APPLIED with a state-mismatch code and can be retried; any other state leaves it UNKNOWN. An UNKNOWN row whose setting is found back at the prior state becomes REVERTED when an application was previously established, otherwise FAILED.

**Force-stop cannot be undone.** It ends the app's processes immediately and nothing in Voltwise restores what the app lost (unsaved state, pending work); the app can start again whenever it is launched or triggered. It is offered only for findings about background runaway or a lingering foreground service, is the one fix marked not reversible, and is never journalled as undoable.

**Persistence.** `insight_actions` survives **Clear history**, which clears findings but keeps the journal, and is never exported or imported. Retention removes only finished rows (REVERTED, FAILED, ONE_SHOT) older than the retention period, plus force-stop rows still UNKNOWN past it (an uncertain force-stop has no Undo or reconciliation); PREPARED, APPLIED and other UNKNOWN rows are kept for Undo, recovery or an unconfirmed outcome. Local rows contain package names; diagnostics, Share report and history export do not.

**Not verified on a device.** Execution through real Shizuku and root, the command output of each Android version and OEM, and the effect of a restricted bucket or app-op on real apps have not been checked on hardware; the JVM tests drive the journal with scripted outputs. See [actual validation](VALIDATION.md).

### Rolling back

- **Schema v9 retires legacy text certification.** Migration 8→9 clears app capture markers and transient snapshots, removes old device-waker attribution rows, and resolves existing active findings. Historical per-app chart rows, ordinary samples/sessions/daily summaries, finding feedback and every action journal remain. Fresh structured captures rebuild app baselines; device findings can be computed again from preserved observations. There is no downgrade migration.
- **Schema v7 is additive and forward-only.** Migration 6→7 only adds nullable columns (session Doze and capture-window times, daily Doze and deep-sleep times, per-app activity counters and the stored top wakelock/alarm/job tags, snapshot Doze counts) and creates four tables (`insight_findings`, `insight_actions`, `snapshot_device_wakers`, `session_device_wakers`); it rewrites no existing row. Existing rows read as unknown (null), not zero. There is no downgrade migration and no destructive fallback, so installing a build that expects schema v6 over a v7 `battery.db` does not downgrade it, and that build will not open the database. To go back, export history first (the newer export is format 5, which an older build may not accept), then clear the app's data or reinstall.
- **Applied settings stay until undone.** Standby buckets, app-op modes and the Doze whitelist belong to Android, not to Voltwise; reverting or uninstalling the app does not reset them, and uninstalling also removes the journal. Undo from the Insights tab while it exists. Without it, the same shell can restore a setting manually: `am set-standby-bucket --user 0 <pkg> <bucket>` (for example `active`, `working_set` or `frequent`), `cmd appops set --user 0 <pkg> RUN_ANY_IN_BACKGROUND default` (adb accepts `default`, which restores the system default; the in-app Undo instead writes back the `allow` or `ignore` it recorded, because the app's allow-list does not permit `default`), and `cmd deviceidle whitelist +<pkg>` to put an app back on the user whitelist. Use `RUN_IN_BACKGROUND` on API 26–27. A force-stop has nothing to roll back.

## Backup and alert preferences

Android backs up databases and app files by default. Both the pre-Android12 backup rules and Android12+ cloud/device-transfer rules explicitly include only the settings DataStore directory. Battery databases and diagnostic files are not included; future diagnostics belong in noBackupFilesDir. Explicit exports remain the user-controlled transfer path. See [Auto Backup rules](https://developer.android.com/identity/data/autobackup).

Android notification-channel sound and vibration are controlled by the user after channel creation. A working settings screen must open the channel settings rather than imply that unrelated preference switches override Android. See [notification channels](https://developer.android.com/develop/ui/compose/notifications/channels).

The monitoring notification's status-bar icon is a small rendered bitmap (a short number of glyphs); SystemUI tints it and uses only its alpha, so its own colour does not matter. Some OEM skins — MIUI in particular — ignore bitmap small icons in the status bar and show the launcher icon instead; on those skins the static `ic_stat_battery` icon is effectively always what's shown, not the live reading. This is OEM behavior Voltwise cannot override.

The monitoring notification is updated in place (same id and channel, no cancel between updates). Every notification of one monitoring session — the startup placeholder, each update and a re-promotion — carries the same nonzero `when`, taken when monitoring starts and renewed only by the next start, and hides it (`setShowWhen(false)`). AOSP 16 reads `when` = 0 as the post's fresh creation time (`Notification.getWhen`), so shades that order by time moved the notification to the top on every refresh. Stock ranking may already hold its position; the fix is aimed at the time-ordered shades of some Android 16 / OEM builds and still needs confirming on such a device.

The high-discharge alert requires at least 3 qualifying readings spanning at least 1 minute before it fires, to avoid firing on a single noisy sample. With the screen off, the sampler only polls every 300 seconds (5 minutes; see [measurement guide](MEASUREMENTS.md)), so in the worst case the alert can lag the actual onset of high discharge by roughly 10–15 minutes (up to two or three poll intervals) rather than the ~1 minute a screen-on user would see.

## Local diagnostics and sharing

Sources and diagnostics shows raw, validated Android battery units and UTC capture times, together with the app observation window and Android's separate batterystats window. These reports do not infer a battery-health percentage or attribute drain from activity duration alone. Unsupported readings remain unavailable.

The local diagnostic log accepts fixed event codes only, keeps the latest 60 entries, groups adjacent repeated conditions and bounds the file to 32 KiB. An AtomicFile in noBackupFilesDir survives normal app restarts without entering Android cloud or device-transfer backups. Writes are coalesced to at most once per minute without a wake lock or alarm; a process interruption can lose recent events. Persistence is not guaranteed within a minute while the CPU is asleep. Storage failure is shown in the screen.

Share report opens Android's chooser only after a user tap. The report contains app/API version, reading units/timestamps, observation coverage, privilege availability and fixed event codes. It excludes app/UID lists, raw system dumps, internal observation/session IDs and device identifiers. Source read failures are represented by status/codes rather than copied command output or exception messages. History clearing does not clear diagnostic events or change Android system statistics.

Implementation references: [AtomicFile integrity and caller-owned synchronization](https://developer.android.com/reference/android/util/AtomicFile), [Room observable query invalidation](https://developer.android.com/training/data-storage/room/async-queries). The diagnostic store has one writer after its initial read; AtomicFile itself supplies no lock.

A normal [Compose BOM platform permits version overrides](https://developer.android.com/develop/ui/compose/bom); merely selecting a stable BOM did not make every resolved component stable. The app/test dependency declarations now enforce the stable BOM together. Inspection of the published settings AAR confirms all45 referenced Material3 members exist in stable1.4.0; runtime revalidation remains required. The earlier teardown exception was secondary to this text-field crash.

Widget validation uses the public [AppWidgetHost](https://developer.android.com/reference/android/appwidget/AppWidgetHost) and [widget binding API](https://developer.android.com/reference/android/appwidget/AppWidgetManager#bindAppWidgetIdIfAllowed(int,%20android.content.ComponentName)) in a disposable test host. It verifies system delivery of production RemoteViews with scripted values; it does not establish Samsung launcher behavior.

A separate CI pass is prepared to verify process page size, native linking and the ordinary/Shizuku suites. It remains unexecuted, and cannot validate ARM64 or physical Samsung hardware.

## Screen event ordering
Android16 [Notifier](https://github.com/aosp-mirror/platform_frameworks_base/blob/android16-release/services/core/java/com/android/server/power/Notifier.java) updates interactive state separately from its asynchronous message/broadcast delivery (`updatePendingBroadcastLocked`, `sendWakeUpBroadcast`). A read can therefore see the new state before Voltwise receives its broadcast. The two-second confirmation allowance is an app policy, not an Android delivery guarantee. It retains the first actual capture; late, missing or conflicting events leave the earlier interval unobserved. Contradictory queued screen events never override the current PowerManager reading. No extra wake lock, alarm or timer is introduced.
