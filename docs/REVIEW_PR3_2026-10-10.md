## Important

1. **Turn on high-battery alert reports Done while notifications are blocked** (silent-failure-hunter).
   - `battery/insights/actions/InsightActionRepository.kt:40-43` calls `alertEnabler()` and journals ONE_SHOT with no check of `Notifier.canPostAlerts` (`battery/util/Notifier.kt:75`).
   - With POST_NOTIFICATIONS denied (API 33+) or the alert channel off, the snackbar and chip say Done and the recommendation counts as applied, but `BatteryMonitorService` never posts.
   - Fix: still enable the setting, but return a distinct result whose message says notifications are off, with the existing EnableNotifications route.
2. **"Open battery optimization settings" can do nothing at all** (silent-failure-hunter).
   - `ui/screens/insights/InsightsScreen.kt:149-157` and `FindingDetailsScreen.kt:163-171` catch `ActivityNotFoundException` and show nothing. Some OEM and Go builds lack `IGNORE_BATTERY_OPTIMIZATION_SETTINGS`.
   - Fix: fall back to `ACTION_SETTINGS` or the app details page, plus a fixed-code message (e.g. `SETTINGS_UNAVAILABLE`). UI ticket.
3. **Incomplete batterystats dumps leave no diagnostic** (silent-failure-hunter).
   - `battery/apps/SessionSnapshotCollector.kt:96-99` skips the baseline with only `log(...)`; `:146-148` stores END non-comparable (`captureStartMs = null`).
   - A device where every dump is incomplete (any UID with counters but no `power_use_item`, or any rejected record) stays "still learning" forever, and the diagnostic report shows nothing.
   - Fix: record a fixed code (new `ADVANCED_INCOMPLETE`, or `ADVANCED_FORMAT_INVALID`) on each downgrade.
4. **App-anomaly and trend detectors lack the seeded false-positive tests that `.claude/live-rules/rules/statistical-detectors.md` requires** (pr-test-analyzer, rated 8 and 7).
   - `engine/detectors/app/AppContext.kt:43-66` `anomaly`: floor × feedback multiplier, z ≥ 3 against a median/MAD baseline from 4+ windows. Used by every app detector, evaluated per app per analysis; HIGH findings notify and offer privileged actions. Changed by SQ-270/SQ-281 without seeded tests.
   - `engine/Trends.kt:63-79` `comparison`: ≥ 4 points per side, floor, ≥ 20% median shift; no dispersion term. Days with ~50% variance can fire with no real change.
   - Tests to add: 500 seeded trials on flat, noisy and AR(1) series, with the bound stated in the test, reported as counts out of N, plus a realistic positive control. The templates are `DeviceDetectorsTest` and `ChargingHealthTest`. If a bound fails, change the rule; never loosen the bound.
5. **The action journal relies on unchecked string links** (type-design-analyzer).
   - The `"CHANGED_EXTERNALLY"` literal is written 7× in `InsightActionRepository.kt` and read in `viewmodel/InsightsRepository.kt:109` to set `changedExternally`. A typo silently hides the "Changed outside Voltwise" label.
   - `model.ActionStatus` is mapped from `db.InsightActionStatus` by name (`InsightInputsBuilder.kt:93`, `enumName<ActionStatus>(it.status.name) ?: return@mapNotNull null`). A status added to only one enum silently drops rows from ActionEffects.
   - Fix: a shared constant or enum for the message column, plus an exhaustive `when` mapping between the two enums.

## Suggestions

- **Stale comments and docs** (comment-analyzer):
  - `ui/screens/insights/InsightsScreen.kt:203` says "n of 4 sessions"; `LEARNING_SESSIONS = AppContext.MIN_ELIGIBLE_WINDOWS` = 5.
  - `docs/MEASUREMENTS.md:101` says unproduced findings are always resolved and a report has at most 12. Since SQ-355, a DOZE_WHITELISTED_DRAINER stays ACTIVE while membership is unknown, and `publish()` shows every ACTIVE row, so a report can exceed 12 (harmless). Also mention that INFO applied-fix effects are ranked first (`InsightEngine.kt:30-33`).
  - `battery/insights/InsightNotifier.kt:31` says pruning "bounds the set to 12 findings"; that no longer holds, for the same reason.
  - `ui/NavGraph.kt:35-36`: the SettingsStatus parenthetical lists too few origins. Insights, FindingDetails, SessionDetails and AppDetails push it too.
  - `docs/MEASUREMENTS.md:113` says "differs from the one last announced"; the code skips every key in `NOTIFIED_KEYS` still in the report.
- **The real `PackageManagerTargetInspector` is untested** (`battery/insights/actions/TargetInspector.kt:21-57`; pr-test-analyzer, 7). It holds the ROLE_HOLDER, SHARED_UID and other-user refusals that keep force-stop and restrict off the keyboard, launcher, dialer and SMS app. Every test uses a fake. Needs an androidTest (`TargetInspectorDeviceTest`).
- **Retention resolution is written three times** against the raw `data_retention_index` key: `viewmodel/SettingsViewModel.kt` (KmpSettingsStore), `battery/data/HistoryRetention.kt:46-48` and `settings/SettingsMigrations.kt:69` (type-design-analyzer). With an out-of-range index, HistoryRetention pauses cleanup while `retentionUnset` is false and Settings shows 90 days. *Unconfirmed* whether the schema decoder passes an out-of-range index through. Fix: one `resolveRetention(prefs)` returning Days, Forever or Unset.
- **Values that should derive from enums are persisted and decoded** (type-design-analyzer):
  - `Evidence.unit` (always `metric.unit`), and `Recommendation.reversible` / `requiresPrivilege` (fixed by `ActionType`, `Recommender.kt:46`), are written and read back by `FindingCodec.kt:26,65,71`.
  - A row stored by an older build can switch Apply on or off by an outdated rule. `apply()` still refuses at runtime, so the effect is UI only.
  - Fix: derive these from the enums on decode.
- **A PREPARED row has no in-process recovery** (silent-failure-hunter, low). If `dao.updateAction(... APPLIED)` throws after a confirmed privileged write (e.g. disk full), the row stays PREPARED. `undo()` and `undoable()` exclude PREPARED, so there is no Undo and the app stays restricted until the next start's `reconcile()`. Fix: treat PREPARED like UNKNOWN in undo, or reconcile that row on the next apply/undo.

Below the bar (code-reviewer, confidence under 80): the "x minutes ago" text is frozen while the screen stays composed (`InsightsScreen.kt:103`, `FindingDetailsScreen.kt:133`); raw `.dp` chart constants in `FindingChart.kt:336-342`.
