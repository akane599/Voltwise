## Important

1. **The fallback notice is shown while the user is away from the app** (code-reviewer at 80, silent-failure-hunter at 85; *verified*).
   - `rememberSettingsOpener` (`ui/screens/insights/SettingsPages.kt:72-86`) starts the Settings activity and only then returns the notice text. The callers then show it as a Short snackbar: `InsightsScreen.kt:91,146` and `FindingDetailsScreen.kt:112`.
   - The snackbar's 4 s timer runs while Settings covers the app. The user lands on Settings home with no guidance, which is the case US-25 meant to fix.
   - `UNAVAILABLE` (nothing opened) is unaffected.
   - Fix (UI ticket): hold the notice and show it as a Long snackbar once the lifecycle reaches RESUMED. Consume it after it's shown, and keep it across recreation, for example in saved state.
   - Not a `Toast`: on API 31+ a text toast is cut to two lines, and an app whose notifications are off has its background toasts dropped. Those are the users who meet this fallback.
2. **A refusal on Shizuku or root records nothing** (silent-failure-hunter at 80, pr-test-analyzer; *verified*).
   - `battery/insights/DozeWhitelistReader.kt:21` returns null without a code when `outcome.mode == NONE || DumpOutput.isRefusal(message)`. That guard was copied from `AppStatsRepository`'s ADB path.
   - Here the mode is already SHIZUKU or ROOT, so `mode == NONE` can never be true.
   - A "Permission Denial" from an OEM SELinux policy or a restricted su context is a real failure, yet it leaves the Doze finding frozen with no trace.
   - Fix: delete the guard so every `Failure` records a code. Update the refusal test to expect the Doze read code from Important 3.
3. **Doze-whitelist failures show on Status as per-app-statistics failures** (silent-failure-hunter at 85; *verified*).
   - `StatusViewModel.kt:224-225` maps `ADVANCED_READ_FAILED` to "Per-app statistics could not be read" and `ADVANCED_FORMAT_INVALID` to "Android's battery report was not understood". Neither describes a whitelist read.
   - This is the cost of reusing those codes, which the earlier review prescribed.
   - The text isn't in the ViewModel: `StatusScreen.kt:433-434` maps each `StatusIssueKind` to a string in `strings_status.xml` (en/es/tr).
   - Fix, logic part: add `DOZE_WHITELIST_READ_FAILED` and map it in `StatusViewModel` to a new `StatusIssueKind`. Alternatively, map it to null like `ADVANCED_INCOMPLETE` if it should appear only in the diagnostic report.
   - Fix, UI part (only for a new kind): a separate Claude ticket for its `StatusScreen.kt` mapping and en/es/tr strings. It depends on the logic ticket.

## Suggestions

- **Test oracle** (pr-test-analyzer, 6). The `undoable()` matrix (`InsightActionRepositoryTest.kt:162`) checks against `type.reversible && type.requiresPrivilege`, which is the formula the code uses. - **Notice → text mapping** (pr-test-analyzer, 4). Nothing tests it; swapping the fallback strings passes every test. Pull out a pure `SettingsNotice.messageRes()` and assert it.
- **Doze diagnostics wiring** (pr-test-analyzer, 4). Nothing tests `AppModules.kt:202`; replacing it with `{}` breaks nothing. Add a case to `InsightsWiringTest`.
- **Undo-before-reconcile ordering** (pr-test-analyzer, 4). Only reconcile-first is pinned. Add the reverse.
- **Comment fixes** (comment-analyzer):
  - `PROGRESS.md` US-25 line: "(journal package)" should be `battery/insights/actions/InsightActionRepository.kt`.
  - `AppAnomalyFalsePositiveTest.kt:281-282` and `docs/MEASUREMENTS.md:81`: StuckWakelock's 4× control is a single evaluated window, not "both persistence windows" and not "sustained".
  - `SettingsPages.kt:53,57-58`: the KDoc leaves out the `UNAVAILABLE` (nothing opened) branch.
- **Small types** (type-design-analyzer):
  - Give `Retention.Days`'s `require` a message.
  - Name the repeated live-status set in `InsightActionRepository.kt` (:18, :84) as a constant. `undoable()` currently allocates a new `listOf` for every row it checks.
  - Three lookups find an `ActionType` by name: `undoable()` uses `enumName`, while `journalOperation` (:269) and `InsightsRepository.kt:107` use `ActionType.entries.firstOrNull`. Use one shared helper.
  - Remove the default from `ActionResult.OneShot.notificationsBlocked`. It has two producers: `InsightActionRepository.kt:52` passes it, and FORCE_STOP at `:74` relies on the default. Have FORCE_STOP pass `false` explicitly.
  - `InsightActionMessage.messageRes()` (`InsightLabels.kt:222`) only forwards to `code.messageRes()`. Inline it at `InsightsScreen.kt:132`.
  - Follow-up: derive `RecommendationState.reversible`/`requiresPrivilege` from `action` (`InsightsUiState.kt:35-41`).
- **Timeouts** (pr-test-analyzer, 3). The 5 s real-time `withTimeout` guards are tighter than `runTest`'s 60 s. Use 30 s to keep the localized failure with more margin on a loaded CI host.

Not adopted: deleting the stored `reversible`/`requiresPrivilege` fields from `RecommendationRow` (type-design-analyzer). US-24 decided to keep them in the stored JSON for compatibility.
